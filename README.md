# prisma-sqlmodel-gen

[![npm version](https://img.shields.io/npm/v/prisma-sqlmodel-gen)](https://www.npmjs.com/package/prisma-sqlmodel-gen)
[![CI](https://github.com/ganesh-rao/prisma-sqlmodel-gen/actions/workflows/ci.yml/badge.svg)](https://github.com/ganesh-rao/prisma-sqlmodel-gen/actions/workflows/ci.yml)

Generate Python `SQLModel` table models from a Prisma 8 contract.

This is the v2 line: Prisma 8 `contract.json` input, PostgreSQL only. If you use Prisma 7 with schema files or MySQL, stay on `prisma-sqlmodel-gen` 0.x, which keeps the schema/DMMF frontend.

## Who needs this?

Use this package if your TypeScript app uses Prisma 8, but another Python service needs matching `SQLModel` models for the same database. It is for teams that want Prisma to stay as the single source of truth instead of hand-maintaining the same schema twice.

## What it does

`prisma-sqlmodel-gen` reads your Prisma 8 `contract.json` file and generates Python `SQLModel` classes from it. It works from the contract file itself, so it needs no live database and no Prisma engines at generation time.

## Quick start

Install:

```bash
npm install -D prisma-sqlmodel-gen
```

npm package:

- https://www.npmjs.com/package/prisma-sqlmodel-gen

Emit the contract from your Prisma 8 project:

```bash
prisma contract emit
```

Run generation:

```bash
prisma-sqlmodel-gen --contract ./contract.json --output ./python_app/generated
```

Or verify generated files in CI:

```bash
prisma-sqlmodel-gen --contract ./contract.json --output ./python_app/generated --check
```

## Recommended workflow

```json
{
  "scripts": {
    "db:contract": "prisma contract emit",
    "models:generate": "prisma-sqlmodel-gen --contract ./contract.json --output ./python_app/generated",
    "models:check": "prisma-sqlmodel-gen --contract ./contract.json --output ./python_app/generated --check"
  }
}
```

`--check` verifies that committed generated files match the current contract and exits nonzero on drift.

## Minimal example

Prisma schema fragment (for context — the generator reads the emitted contract, not this file):

```prisma
model User {
  id    Int    @id @default(autoincrement())
  email String @unique @db.VarChar(255)

  @@map("users")
}
```

```bash
prisma contract emit
prisma-sqlmodel-gen --contract ./contract.json --output ./python_app/generated --no-emit-init
```

Representative generated output (byte-for-byte deterministic):

```python
# This file is generated by prisma-sqlmodel-gen.
# Package version: 2.0.0
# Schema hash: f771defb09d3
# Module: models.py
# Do not edit this file directly.

from typing import Any, Optional
from sqlmodel import Field, Relationship, SQLModel
from sqlalchemy import Column
from sqlalchemy.dialects.postgresql import INTEGER, VARCHAR

class User(SQLModel, table=True):
    __tablename__ = 'users'
    email: str = Field(sa_column=Column(VARCHAR(255), unique=True, nullable=False))
    id: int | None = Field(sa_column=Column(INTEGER(), primary_key=True, nullable=False, autoincrement=True), default=None)
```

## CLI reference

```bash
prisma-sqlmodel-gen --contract <path> [options]
```

| Option | Default | Description |
| --- | --- | --- |
| `--contract <path>` | (required) | Path to the Prisma 8 `contract.json` file. |
| `--output <dir>` | `<contractDir>/generated/sqlmodel` | Directory for generated files. |
| `--module-name <name>` | `models.py` | Generated module file name. |
| `--check` | off | Verify committed files match instead of writing. |
| `--emit-init` / `--no-emit-init` | emit | Write or skip the `__init__.py` re-export file. |

Exit code is nonzero when contract validation fails, when generation hits an unsupported construct, or when `--check` finds drift.

## Programmatic API

```ts
import { readFile } from "node:fs/promises";
import { generateSqlModel, resolveGeneratorConfig } from "prisma-sqlmodel-gen";

const contractText = await readFile("./contract.json", "utf8");
await generateSqlModel({
  contractPath: "./contract.json",
  contractText,
  outputDir: "./python_app/generated",
  config: resolveGeneratorConfig({ moduleName: "models.py" })
});
```

`checkSqlModelGeneration` takes the same input and throws when output is stale or missing instead of writing. `resolveGeneratorConfig` fills defaults (`models.py`, emit init file, header comment, strict mode). The package root also exports `parseContractDocument`, `buildSchemaDefinitionFromContract`, `renderPythonModule`, diagnostics helpers, and all input/output types.

## Support matrix

Runtime targets:

- Prisma 8 contracts (`schemaVersion` 1, `sql`/`postgres` target)
- Node 22+
- Python 3.11+
- PostgreSQL only (no MySQL in v2)

Generated artifacts:

- `models.py`
- `__init__.py` (unless `--no-emit-init`)

Mode:

- strict generation with hard failures for unsupported constructs
- deterministic output intended for commit-and-review workflows

Validation matrix:

- Offline packed-install suite: real CLI runs over every contract fixture, determinism, `--check`, error paths, Python syntax validation
- Online docker-backed suite: generated models validated against live PostgreSQL 16 on Python 3.12 with current `sqlmodel` (0.0.46 at the time of writing)

## Supported features

Fully supported contract features:

- mapped tables and columns
- non-public PostgreSQL schemas
- native, text, and integer enums, including enum defaults
- scalar and enum lists via PostgreSQL arrays
- one-to-one, one-to-many, and many-to-one relations
- explicit many-to-many join models rendered as navigable relations (`link_model` when the contract carries many-to-many metadata)
- one-sided relations (rendered without `back_populates`)
- self-relations (`remote_side`)
- named and composite foreign keys with `onDelete` / `onUpdate`
- named primary keys, unique constraints, and indexes
- expression, partial (`WHERE`), access-method (`USING`), and sorted indexes
- check constraints
- value objects and single-table / joined-table inheritance variants
- literal and enum-member defaults, `autoincrement()`, `now()`, `uuid()`, client-side timestamp/uuid factories, auto-updated timestamps, and raw SQL server defaults
- `Json` / `Jsonb` columns and PostgreSQL native column types
- strict diagnostics with machine-readable codes

Intentionally strict (generation fails instead of guessing):

| Feature | Behavior |
| --- | --- |
| Unknown storage column types | Hard fail |
| Unresolvable relation targets or join models | Hard fail in strict mode, skipped when `strict: false` |
| `ulid()` / `nanoid()` client defaults | Hard fail |
| Unknown execution defaults | Hard fail |
| Defaults on composite primary keys | Hard fail in strict mode |
| Python name collisions after sanitization | Hard fail |
| Non-PostgreSQL contract targets | Hard fail |
| Invalid JSON, wrong version, non-object documents | Hard fail |

Out of scope for v2:

- MySQL (stays on the 0.x line)
- Implicit many-to-many (contracts describe explicit join models)
- Prisma-client-only concepts (they are not present in contracts)
- DTO classes (`Create` / `Update` / `Read`); table models only

## Porting a Prisma 7 schema

v2 reads `contract.json` emitted by Prisma 8, so a v7 `schema.prisma` must first be ported to Prisma 8 PSL. The rules below are verified against `prisma contract emit` (8.0.0-rc.15); the `tests/fixtures/contracts/user-schema.*` trio records a real 4-model v7 schema, its v8 port, and the emitted contract:

- drop the `datasource db` block (forbidden in v8; the connection lives in `prisma.config.ts`) and any `generator` blocks (irrelevant to emit), and add the `// use prisma-8` header
- move native types to type position: `String @db.Uuid` becomes `Uuid`, `DateTime @db.Timestamp(6)` becomes `Timestamp(6)`, `String @db.VarChar(n)` becomes `VarChar(n)`, `DateTime @db.Date` becomes `Date`
- write index access methods as lowercase strings: `type: Gin` becomes `type: "gin"`
- port every `Json` column to `Jsonb` to keep v7 semantics: v7 stores `Json` as `jsonb`, while v8 splits `Json` (`json`) from `Jsonb` (`jsonb`), and `gin` has no operator class for plain `json`

One v7 construct is currently unportable: per-column index sort direction (`field(sort: Desc)`) has no spelling in this Prisma 8 RC (field arguments in `@@index` are rejected and there is no `sort:` argument), so sorted indexes port to plain column lists. The contract is otherwise lossless: exact index/constraint names, access methods, mapped names, and composites all survive the round trip.

## Known limitations

The generator stays in strict mode by default. The CLI is always strict; programmatic callers can pass `strict: false` to skip unresolvable relations and join models, but unsupported constructs still fail. If a contract feature cannot be represented 1:1 in SQLModel/SQLAlchemy metadata or ORM behavior, generation fails instead of degrading silently.

The contract file is the single source of truth: regenerate after every migration or contract change, and never hand-edit generated files.

## Diagnostics

Failures include:

- machine-readable diagnostic codes
- model and field context
- a short remediation suggestion when one is available

Example:

```text
ERROR UNRESOLVED_RELATION_TARGET (A.ghost): Relation 'ghost' points to 'Missing', which is not declared in the contract. Suggestion: Declare the target model in the contract or run in non-strict mode to skip the relation.
```

## Troubleshooting

- `CONTRACT_JSON_PARSE_ERROR`
  The contract file is not valid JSON. Re-emit it and check for truncation or hand edits.
- `UNSUPPORTED_CONTRACT_VERSION` / `UNSUPPORTED_CONTRACT_TARGET`
  Regenerate with a supported Prisma 8 toolchain. Only `sql`/`postgres` contracts are accepted; MySQL projects stay on the 0.x line.
- `UNKNOWN_COLUMN_TYPE`
  The contract uses a storage type with no SQLAlchemy mapping (for example an extension type). Use a supported PostgreSQL column type.
- `PYTHON_TYPE_NAME_COLLISION` / `PYTHON_FIELD_NAME_COLLISION` / `PYTHON_ENUM_VALUE_COLLISION`
  Rename the conflicting models, fields, or enum values so they stay distinct after Python identifier sanitization.
- stale output in `--check`
  Regenerate from the current contract and commit the refreshed files.

## Python runtime notes

PostgreSQL `uuid` columns render as `PG_UUID` (imported as `UUID as PG_UUID`) so the `uuid.UUID` annotation keeps working; without the alias the column type would shadow the annotation and pydantic would fail at import.

Your Python application still needs to install its own runtime dependencies, for example:

```bash
pip install "sqlmodel==0.0.46" "psycopg[binary]"
```

The generated code is validated against current `sqlmodel` releases by the docker-backed integration suite (`0.0.46` at the time of writing). If you use a different version, treat it as unvalidated until you run that suite against it. Choose the database driver appropriate for your environment.

## Project structure

- Generated Python modules are fully owned by the generator.
- Handwritten Python business logic should live in separate wrapper modules.
- Regenerate after every successful migration or contract change.

Internal source layout:

- `src/index.ts` library entrypoint
- `src/cli.ts` contract-driven standalone CLI
- `src/generate.ts` file generation and `--check` verification
- `src/contract.ts` contract parsing and validation
- `src/normalize-contract.ts` contract-to-IR normalization
- `src/render-python.ts` Python emission
- `src/config.ts`, `src/diagnostics.ts`, `src/fs.ts`, `src/utils.ts`, `src/version.ts`, `src/types.ts` shared plumbing and types

## Notes

- This generator currently emits table models only.
- It does not emit `Create`, `Update`, or `Read` DTO classes.
